## 一、产品定位

### 1.1 一句话定义

**Omnis** 是一款基于 RAG（检索增强生成）的企业级智能客服平台，通过“可观测的知识问答 + 人机无缝协同 + 负反馈自学习”，让 AI 客服**答得准、看得清、越用越聪明**。

### 1.2 核心主张

| 传统痛点 | Omnis 的主张 |
|:---|:---|
| AI 答非所问，像个“高级复读机” | **答得准**：RAG 混合检索 + 知识边界约束，拒绝幻觉 |
| 回答了也不敢信，找不到依据 | **看得清**：每条回答带原文引用，鼠标悬停即见出处 |
| 转人工后用户要复述三遍问题 | **接得住**：AI 自动生成摘要，人工无缝继承上下文 |
| 知识库越用越“呆”，全靠人工喂 | **学得快**：负反馈驱动自学习，差评自动触发知识补全 |
| 数据泄露风险：客服看到不该看的 | **守得住**：文档级 ACL + 检索阶段强制权限过滤 |

### 3.2 核心功能详解

#### 能力一：RAG 准确问答（解决“答不准”）

**用户问题**：“我的订单什么时候能到？”

**传统客服**：检索“物流”关键词，返回一堆物流政策的链接，用户点开自己找。

**Omnis**：

1. 识别用户身份，自动获取订单号
2. 检索知识库 + 订单系统实时数据
3. 生成回答：“您的订单 #A10086 已发货，预计 5 月 14 日送达，物流单号 SF1234567890【查看详情】”

**关键技术**：

| 技术点 | 说明 |
|:---|:---|
| 混合检索 | 向量检索（语义理解）+ BM25（关键词匹配），双重保障 |
| 查询改写 | 自动补全上下文、分解复杂问题、纠正错别字 |
| 知识边界 | 可配置“仅使用知识库回答”，禁止 LLM 用自己的知识编造 |
| 置信度评分 | 0-1 分，低于 0.6 强制推荐转人工 |

---

#### 能力二：透明化溯源（解决“不敢信”）

**用户收到的回答**：

> 根据退货政策【1】，您购买的商品支持 7 天无理由退货。申请路径：我的订单 > 申请售后【2】。

**鼠标悬停【1】** → 浮窗显示：

> 引用来源：《售后政策 V3.2》第 2 章第 3 条：“用户签收后 7 日内，商品完好不影响二次销售，可申请无理由退货。”

**点击【2】** → 跳转到知识库原文位置。

**价值**：

- 用户：看得见出处，建立信任
- 客服：不用亲自查政策，直接引用
- 质检：纠纷时可追溯原文，判定责任

---

#### 能力三：无缝人工接管（解决“转人工断档”）

**场景**：用户咨询 5 轮后说“转人工”，AI 自动处理：

**Step 1 - 自动生成会话摘要**
【会话摘要】
用户：张三 (VIP)
意图：申请退货
已确认信息：订单号 A10086，商品 T 恤白色 M 码
未解决问题：用户要求“上门取件”但系统显示需“自行寄回”
推荐话术：“很抱歉给您带来不便，VIP 用户可以享受免费上门取件，我马上为您安排。”

text

**Step 2 - 人工坐席工作台自动加载**

- 左侧：会话列表（标红等待超 2 分钟）
- 中部：聊天记录 + AI 自动生成的摘要卡片
- 右侧：知识库推荐 + 快捷回复 + 用户画像

**Step 3 - AI 静默辅助**

- 人工回复时，AI 在后台持续推荐答案
- 人工只需点击即可发送，不用自己打字
- 人工回复后，AI 自动暂停，不干扰

**价值**：转人工后用户**无需复述**，人工**无需重复查询**，效率提升 50%+。

---

#### 能力四：负反馈自学习（解决“越用越蠢”）

**反馈闭环流程**：
用户点“没用”
│
▼
系统自动记录：问题 + AI 回答 + 检索到的文档
│
▼
触发“低质量告警”，存入待审核队列
│
▼
知识管理员收到通知：「有 12 条低分回答待审核」
│
├── 问题类型 A：知识缺失 → 补充新文档
├── 问题类型 B：检索错误 → 优化分片/权重
└── 问题类型 C：LLM 生成错误 → 调整提示词
│
▼
重新发布后 → 该问题后续回答正确

text

**未命中自动聚类**：

- 连续 3 次触发兜底回答（“我没有找到答案”）
- 系统自动聚类相似问题，生成“**知识缺口报告**”
- 示例报告：「过去 24 小时，12 人问“优惠券叠加规则”，知识库未覆盖」

**价值**：知识管理员不用靠猜，系统告诉你要补什么。

---

#### 能力五：文档级权限控制（解决“数据泄露”）

**场景**：同一企业内，HR 系统的员工薪资文档只能 HR 部门查看。

**权限模型**：

| 文档 | 可见范围 | 谁能检索到 |
|:---|:---|:---|
| 《公司福利手册》 | 全员 | 所有人 |
| 《薪资结构说明》 | HR 部门 + 财务部 | 仅 HR 和财务 |
| 《CEO 候选人评估》 | CEO + 董事会 | 仅 2 人 |

**技术实现**：

- 每个文档分片（Chunk）存储 `allow_groups` 和 `deny_users` 标签
- RAG 检索时，强制注入当前用户的 `user_id` 和 `groups`
- SQL/向量查询的 `WHERE` 条件中自动追加权限过滤
- **禁止**先检索再过滤（防止侧信道泄露）

**价值**：

- 员工：通过客服问“我的薪资” → 只能看到自己的
- HR：通过客服问“张三的薪资” → 能查到（如果有权限）
- 外部用户：永远看不到内部文档

---

#### 能力六：RAG 可观测性（解决“黑盒调试”）

**痛点**：AI 回答错了，但不知道是“没搜到”还是“没生成好”。

**Omnis 观测面板**：

每次问答都记录完整链路，管理员可在后台查看：
┌─────────────────────────────────────────────────────────┐
│ 用户问题：“怎么退款” │
├─────────────────────────────────────────────────────────┤
│ 检索结果（Top 3）： │
│ 1. 《退货流程》 相似度 0.92 ← 正确但不完全匹配 │
│ 2. 《退款到账时间》 相似度 0.45 ← 不相关 │
│ 3. 《售后政策》 相似度 0.38 ← 不相关 │
├─────────────────────────────────────────────────────────┤
│ 最终 Prompt（发送给 LLM）： │
│ "基于以下上下文回答问题：1. 退货流程... 2. 退款到账时间..." │
├─────────────────────────────────────────────────────────┤
│ LLM 输出：“根据退货流程，您需要先申请退货...” │
├─────────────────────────────────────────────────────────┤
│ 分析诊断： │
│ ⚠️ 检索结果 Top 1 是“退货”而非“退款”，导致答案偏了方向 │
│ 💡 建议：补充“退款”相关的 FAQ 文档 │
└─────────────────────────────────────────────────────────┘

text

**价值**：从“凭感觉优化”变成“数据驱动优化”。

### 6.2 电商零售案例：某头部电商平台

**客户背景**

- 行业：综合电商平台
- 用户规模：亿级注册用户
- 客服团队：2,000+ 人

**业务痛点**

| 痛点 | 表现 |
|:---|:---|
| 大促期间咨询量暴增 | 双11期间日咨询量达平时的15倍，人工排队超30分钟 |
| 重复问题消耗人力 | 60%咨询为“物流查询”“退换货流程”“优惠券使用规则” |
| 客服培训成本高 | 品类多、促销规则复杂（满减/拼单/预售），新客服上岗慢 |
| 售后纠纷无据可查 | 用户称“客服说过可以退货”，但无法追溯 |

**Omnis 解决方案**

**1. 知识库建设**

- 导入：商品库（百万级SKU）、促销规则文档（200+）、退换货政策、物流合作协议
- 结构化：按品类、促销类型、售后类型建立分类标签

**2. 智能问答场景**

- 行业：人寿保险 + 财险
- 用户规模：3,000 万投保人
- 业务特点：高合规要求、敏感数据多

**业务痛点**

| 痛点 | 表现 |
|:---|:---|
| 权限安全要求极高 | 代理人不能查看其他代理人的客户，用户只能看自己的保单 |
| 理赔流程复杂 | 不同险种所需材料不同，用户反复问“需要什么材料” |
| 合规审计压力大 | 保险条款必须一字不差，AI 错解可能引发法律风险 |
| 代理人咨询量大 | 30万代理人每天问“XX产品佣金怎么算”“XX客户能投保吗” |

**Omnis 解决方案**

**1. 多层权限隔离**

- 租户层：寿险团队 vs 财险团队，数据完全隔离
- 用户层：普通用户仅能查询自己的保单
- 代理人层：仅能查询自己名下的客户
- 实现方式：检索阶段强制注入 `user_id` / `agent_id` 过滤条件

**2. 证据链固化**

- 所有理赔相关的 AI 回答，自动生成 PDF 证据包
- 证据包含：用户问题、AI 回答、引用的保险条款原文（带截图）、时间戳、审计 ID
- 法律效力：可作为纠纷认定的辅助依据

**3. 保险术语增强**

- 构建保险领域同义词库（“重疾” = “重大疾病” = “重症”）
- 查询改写时自动扩展，提升检索召回率
