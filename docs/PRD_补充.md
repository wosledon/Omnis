## 1. 产品概述

### 1.1 产品定义

Omnis 是一款基于 RAG 的智能客服平台。不仅提供标准的知识问答，更通过 **"可观测的RAG流水线"** 和 **"人机协同闭环"** ，解决传统AI客服的"黑盒体验"和"知识停滞"问题。

### 1.2 核心价值（痛点映射）

| 核心价值 | 解决的行业痛点 |
|:---|:---|
| **统一知识引擎** | 知识孤岛，FAQ与文档割裂，不同渠道答案不一致 |
| **RAG 增强回答** | 纯大模型产生"幻觉"，关键词搜索答非所问 |
| **透明化溯源** | 大模型"黑盒"：回答看似正确但找不到依据，坐席不敢转发 |
| **无缝接管** | 转人工掉线：用户被迫重复描述问题，AI总结能力弱，人工效率低 |
| **负反馈闭环** | 知识"越用越蠢"：用户点踩/转人工后，知识库无法自动优化 |
| **LLM 无关性** | 被单一云厂商绑定，私有化部署成本高 |

### 1.3 目标用户

| 角色 | 核心诉求 | 痛点关注点 |
|:---|:---|:---|
| 终端用户 | 快速获得准确回答 | 不要让我排队，不要让我重复说了三遍的问题 |
| 一线坐席 | 高效解决问题，背锅少 | 不要给我看AI生成的"废话"，我要直接能看到引用的原文 |
| 知识管理员 | 高效管理知识、监控质量 | 到底是LLM没生成好，还是没检索到？我要知道哪里断了 |
| 系统管理员 | 灵活配置、安全可控 | 确保VIP客户的合同数据不会被普通客服检索到（权限穿透） |
| 质检/合规官 | 确保回答不违规，出现纠纷可复盘 | 高危对话审计，AI回答的证据链必须完整 |

### 2.2 核心模块详细设计

#### M1 - 知识管理模块

**功能描述**：负责企业知识的采集、处理、存储和维护。

| 功能点 | 描述 | 优先级 |
|:---|:---|:---|
| 文档导入 | 支持 PDF/Word/Excel/PPT/Markdown/TXT 上传，自动解析提取内容 | P0 |
| 网页抓取 | 输入 URL 自动抓取网页内容，支持定时同步 | P1 |
| 数据源连接 | 对接 MySQL/PostgreSQL/ES 等数据库，定时同步结构化数据 | P1 |
| API 数据源 | 配置 REST API 作为数据源，支持定时拉取 | P2 |
| 文档分片 | 智能分片策略（按段落/语义/固定长度），支持自定义分片规则 | P0 |
| 向量化 | 文档分片后自动向量化，支持自定义 Embedding 模型 | P0 |
| 知识分类 | 按业务线/主题/租户组织知识，支持标签和目录树 | P0 |
| 版本管理 | 知识文档版本控制，支持回滚 | P2 |
| 质量监控 | 知识命中率、未覆盖问题统计，辅助发现知识缺口 | P1 |
| 文档权限 | 文档级访问控制，支持公开/指定角色/指定用户三种权限模式 | P0 |
| 权限继承 | 知识库权限默认继承到文档，文档可单独覆盖 | P0 |
| 权限审计 | 文档访问/修改/权限变更的操作审计日志 | P1 |

##### 痛点解决：RAG检索到用户无权查看的文档（数据泄露风险）

**解决方案：列级安全策略（RLS）与上下文注入**

- 在向量库中为每个 `Chunk` 存储 `AllowGroups` 和 `DenyUsers` 标签。
- **检索阶段强制过滤**：RAG 引擎检索时，必须携带当前用户的 `User.Id` 和 `Groups`，在 SQL/Vector 查询的 `WHERE` 子句中强制加入 `@user_id IN allow_list`。
- **严禁后过滤**：禁止先检索 Top 100 再在内存中过滤，因为这会泄露敏感数据的存在性（虽然看不到内容，但知道"有一条关于CEO薪资的文档"也是泄露）。

**文档权限模型**：

```text
知识库 (KnowledgeBase)
│
├── 权限设置：默认访问策略（公开/仅成员/自定义）
│
├── 文档 (Document)
│ │
│ ├── Visibility（可见性）
│ │ ├── Public ── 知识库内所有成员可访问
│ │ ├── Internal ── 仅指定角色可访问
│ │ └── Private ── 仅指定用户/用户组可访问
│ │
│ ├── ACL（访问控制列表）
│ │ ├── PrincipalType: User | UserGroup | Role
│ │ ├── PrincipalId
│ │ └── Permission: Read | Edit | Delete | Share | Admin
│ │
│ └── 继承规则
│ ├── 默认继承知识库权限
│ └── 文档级 ACL 可覆盖继承权限（更严格优先）
│
└── 分片 (Chunk)
└── 权限从文档继承，不可单独设置
```

> **关键约束**：RAG 检索时必须在检索阶段注入用户权限上下文，确保用户只能检索到有权限的文档内容，而非检索后再过滤。

**文档处理流程**：

```text
上传/抓取/同步
│
▼
格式解析（PDF/Word/HTML/...）
│
▼
内容清洗（去重/去噪/格式化）
│
▼
智能分片（段落/语义/滑动窗口）
│
▼
向量化（Embedding）
│
▼
存储（向量库 + 原文库）
│
▼
索引更新
```

#### M2 - RAG 引擎模块

**功能描述**：负责检索增强生成的核心推理流程。

| 功能点 | 描述 | 优先级 |
|:---|:---|:---|
| 查询改写 | 对用户问题进行改写、扩展、分解，提升检索召回率 | P0 |
| 混合检索 | 向量检索 + 关键词检索（BM25）融合，支持权重可配 | P0 |
| 重排序 | 对检索结果进行 Rerank，提升相关性排序 | P1 |
| 答案生成 | 基于检索上下文，调用 LLM 生成结构化回答 | P0 |
| 引用溯源 | 回答中标注来源文档/段落，支持跳转查看原文 | P0 |
| 多轮上下文 | 结合对话历史进行检索和生成，维持多轮语义连贯 | P0 |
| 未命中兜底 | 检索无结果时触发兜底策略（转人工/提示无答案/推荐相关） | P1 |
| 知识边界 | 可配置是否允许 LLM 使用自身知识回答，还是仅限知识库 | P0 |
| 权限过滤检索 | 检索阶段注入用户权限上下文，仅召回有权文档的分片 | P0 |

##### 痛点解决：客服不敢用AI生成的回答（缺乏信任）

**解决方案：颗粒化引用 & 高亮溯源**

- 要求 LLM 在生成最终回答时，必须通过特殊标记 `【source-123】` 标注引用来源。
- 前端渲染时，鼠标悬停在引用标号上，**浮窗显示原文片段**，点击跳转知识库原文。
- **增加可信度分数**：返回 `ConfidenceScore` (0-1分)，由检索相似度 (40%) + 答案完整性 (30%) + LLM 自评 (30%) 加权得出。低于 0.6 分强制建议转人工。

##### 痛点解决：知识库出错了，但不知道是"没搜到"还是"没生成好"

**解决方案：完整的观测流水线 (RAG Observation Pipeline)**

- 存储每一次问答的 **"请求指纹"**：
  1. **Input**：用户问题 (Query)
  2. **Retrieval Context**：检索到的 Top 5 Chunk 内容及相似度分数
  3. **Prompt**：组装后发给LLM的完整 Prompt
  4. **Output**：LLM 原始输出
  5. **Final Answer**：后处理后的回答
- **调试视图**：在管理后台的"对话详情"中，增加 **"RAG 调试"面板**，供知识管理员回溯："哦，原来是用户问的是'怎么退款'，但检索出来的 Top 1 是'退货流程'，两个相似度只有0.6，难怪答错了。"

**RAG 推理流程**：

```text
用户提问
│
▼
查询改写（Query Rewriting）
│
├── 问题分解（Multi-Query）
│
▼
混合检索（Hybrid Search）
│
├── 注入用户权限上下文（可访问的文档/知识库列表）
├── 向量检索（语义相似度 Top-K，带权限过滤）
├── 关键词检索（BM25 Top-K，带权限过滤）
│
▼
结果融合 + 重排序（Rerank）
│
▼
上下文组装（Prompt Engineering）
│
├── 系统提示词（角色/规则/约束）
├── 检索结果（Top-N 文档片段）
├── 对话历史（近 N 轮）
│
▼
LLM 生成回答
│
▼
后处理（引用标注/格式化/敏感词过滤）
│
▼
返回给用户
```

#### M3 - 对话引擎模块

**功能描述**：负责对话会话管理、多轮交互和渠道适配。

| 功能点 | 描述 | 优先级 |
|:---|:---|:---|
| 会话管理 | 创建/查询/关闭会话，维护会话状态 | P0 |
| 多轮对话 | 基于上下文的多轮连续对话 | P0 |
| 流式响应 | 支持 SSE/WebSocket 流式返回，打字机效果 | P0 |
| 意图识别 | 识别用户意图，路由到对应处理流程 | P1 |
| 人工转接 | 无法回答或用户要求时，转接人工客服 | P1 |
| 满意度评价 | 对话结束后用户评价，支持差评回访 | P2 |
| 对话历史 | 用户可查看历史对话记录 | P0 |
| 快捷指令 | 预设常用指令（如 /help、/feedback） | P2 |

##### 痛点解决：转人工时，用户要跟人工客服重新说一遍问题

**解决方案：智能副驾模式**

- **自动摘要**：当触发转人工时（用户说"转人工"或连续否定3次），系统**自动生成**会话摘要（用户身份、意图、已解决/未解决部分、关键参数）。
- **上下文继承**：人工客服接入时，工作台直接加载这个摘要 + 最近10轮对话记录 + AI推荐的3条回复话术。
- **静默监听**：人工客服回复时，AI 在后台持续检索知识库并推荐答案，人工只需点击即可发送。人工回复后，AI 暂停生成，避免干扰。

##### 痛点解决：用户问的问题，知识库没有，AI 开始编造

**解决方案：确定性边界策略**

- 在 Prompt 中硬约束：

  > 如果检索到的上下文与问题完全不相关（Top 1 相似度 < 0.5），请回答"抱歉，我没在知识库中找到关于[问题核心词]的答案，您可以点击转人工获取帮助。"

- **严禁**为了"礼貌"而进行无关回答（如"您好，请问有什么可以帮您？"）。

## 3. 数据飞轮与智能化

### 3.1 痛点：知识库越用越差，全靠人工录入

**解决方案：负反馈驱动的自学习管道**

| 反馈类型 | 系统自动动作 | 管理员介入 |
|:---|:---|:---|
| 用户点击 **有用** | 将该 Q&A 对存入"优质问答池"，提升对应 Chunk 在后续检索中的权重 | 无（自动） |
| 用户点击 **没用** | 触发"低质量告警"，将该问答存入"待审核池"，暂时冷冻该回答 | 管理员修正知识库后，重新发布 |
| 连续 3 次未命中（兜底） | 自动聚类相似问题，生成"**知识缺口报告**" | 管理员根据报告批量补充 FAQ |
| 转人工后人工回复 | AI 对比"AI 回答"与"人工最终回答"，标记差异点 | 差异点推送给知识管理员，用于微调 |

## 4. 非功能需求

### 4.1 性能要求

| 指标 | 目标值 | 备注 |
|:---|:---|:---|
| 首次响应时间（TTFT） | < 800ms（流式首 Token） | 包含检索 + LLM 推理首字 |
| RAG 检索延迟 | < 200ms（P95） | - |
| 端到端回答延迟 | < 5s | 含 LLM 生成完整回答 |
| 并发会话数 | ≥ 1000 / 租户 | - |
| 向量检索 QPS | ≥ 5000 | - |
| 系统可用性 | ≥ 99.9% | - |
| RAG 观测写入 | 异步批量写入，不阻塞主回答链路 | 观测数据对主流程透明，失败不影响主流程 |
| 权限过滤检索 | 检索阶段强制生效，< 250ms | 采用向量库原生 RBAC 能力，禁止应用层过滤 |

### 4.2 安全与合规要求

| 要求 | 描述 |
|:---|:---|
| 证据链固化 | 涉及售前承诺/售后理赔的AI对话，自动生成不可篡改的 RAG 证据包（PDF），包含用户问题、AI回答、引用的文档截图 |
| 高危拦截 | 检测用户输入或 LLM 输出中的高危词（政治、竞品刺探、过激投诉），秒级阻断并将会话转接给合规主管 |
| 操作日志 | 知识库的每一次修改、人工客服的每一次"强制采纳"AI建议，均记录审计 |
| 数据加密 | 传输层 TLS 1.2+，存储层 AES-256 |
| 访问控制 | OAuth 2.0 / OIDC 认证，RBAC 授权 |
| 敏感信息 | 对话中自动检测并脱敏敏感信息（手机号/身份证等） |
| 内容安全 | LLM 输出内容安全过滤，防止有害内容输出 |

### 4.3 可扩展性

- 微服务架构，各模块独立扩缩容

- LLM 网关支持动态添加模型
- 渠道接入采用插件机制，便于扩展新渠道

### 5.4 RAG 观测表（核心运维数据）

```sql
-- RAG 推理流水表
CREATE TABLE rag_inference_log (
    id UUID PRIMARY KEY,
    tenant_id VARCHAR(64) NOT NULL,
    session_id VARCHAR(64),
    user_question TEXT,
    rewritten_query TEXT,
    
    -- 检索阶段明细
    retrieved_chunks JSONB,  -- [{chunk_id, content_preview, vector_score, bm25_score, doc_link}]
    
    -- 组装阶段
    final_prompt TEXT,
    
    -- 生成阶段
    llm_raw_output TEXT,
    final_answer TEXT,
    confidence_score DECIMAL(3,2),
    
    -- 归因分析
    citation_source_ids TEXT[],  -- 实际被引用的chunk ID列表
    has_hallucination BOOLEAN,    -- 是否检出了疑似幻觉（引用不存在的内容）
    
    inference_duration_ms INTEGER,
    created_at TIMESTAMP
);

-- 索引：租户 + 时间 + 低置信度
CREATE INDEX idx_rag_log_tenant_time ON rag_inference_log(tenant_id, created_at DESC);
CREATE INDEX idx_rag_log_confidence ON rag_inference_log(confidence_score) WHERE confidence_score < 0.6;
```

## 6. MVP 范围

### 6.1 MVP 功能清单

| 模块 | 功能 | 优先级 |
|:---|:---|:---|
| 知识管理 | 文档上传（PDF/TXT/Markdown）、自动分片、向量化 | P0 |
| 文档权限 | 文档级 ACL、权限继承、检索时权限过滤 | P0 |
| RAG 引擎 | 混合检索、答案生成、引用溯源、多轮上下文 | P0 |
| RAG 观测 | 记录检索详情 & 调试视图 | P0 |
| 引用溯源 | Markdown 标注 + 前端浮窗显示 | P0 |
| 转人工摘要 | 自动生成摘要 + 上下文平滑传递 | P0 |
| 负反馈闭环 | 点踩自动忽略 + 生成"待审核"工单 | P0 |
| 对话引擎 | 会话管理、流式响应、对话历史 | P0 |
| 渠道 | Web Widget、REST API | P0 |
| LLM 网关 | OpenAI / Azure OpenAI 接入、模型配置 | P0 |
| 多租户 | 单租户 + 业务空间隔离 | P0 |
| 管理后台 | 知识库管理、对话管理、系统配置 | P0 |

### 6.2 MVP 不包含

- 微信/钉钉/飞书等 IM 渠道集成
- 人工坐席的复杂技能组路由（初期支持单一队列即可）
- 多轮对话的槽位填充（除非极其简单的查单场景）
- 实时语音质检（成本过高，优先级低）
- 多租户计费系统
- 知识图谱
- 网页抓取 / 数据库数据源
- 知识版本管理
- 满意度评价系统

### 6.3 版本规划

| 版本 | 里程碑 | 核心内容 |
|:---|:---|:---|
| v0.1 MVP | 基础可用 | 单租户 RAG 客服 + Web Widget + 管理后台 + 观测闭环 |
| v0.5 | 多渠道 | + 微信/企微渠道 + 人工转接 + 多 LLM 支持 |

## 8. 总结

这份 PRD 在扎实的技术架构基础上，重点补充了 "可观测性" 和 "人机交互体验" 两块。

当前市面上大部分竞品比拼的是"谁能连更多的渠道"，而 Omnis 的差异化在于"谁能把每一次 AI 回答解释得清清楚楚，并且越用越聪明"。
